# Как объяснить проект преподавателю

## Маршрут одного запроса

1. Браузер открывает `/Movies`: MVC направляет запрос в `MoviesController.Index`.
2. Контроллер выбирает из SQLite будущие сеансы, фильтрует дату и жанр и собирает `ScheduleModel`.
3. Razor `Views/Movies/Index.cshtml` формирует HTML. CSS отвечает за оформление, JavaScript — за меню, слайдер, кресла и сумму на экране.
4. При покупке `BookingController` вызывает `BookingService`. Цена и доступность определяются заново на сервере, а не по значению в браузере.

Identity — готовая подсистема регистрации, хеширования пароля, cookie и ролей. Она использует тот же DbContext и SQLite, что и данные кинотеатра.

## Главное в базе данных

Фильм не равен сеансу: один фильм показывается много раз в разных залах. Кресло принадлежит залу; его занятость относится к паре **сеанс + кресло**. Поэтому `BookingSeat` хранит оба идентификатора. Заказ содержит несколько `BookingSeat`: три выбранных кресла дают три электронных билета.

Внешние ключи имеют `Restrict`: нельзя удалить фильм, зал или сеанс и оставить заказ со ссылкой в пустоту. Именованные индексы ускоряют поиск будущих сеансов, историю пользователя, отзывы и очистку истёкших броней.

## Почему два человека не получат одно кресло

В `CreateAsync` до чтения мест начинается недеферрированная транзакция SQLite (BEGIN IMMEDIATE). SQLite разрешает одного писателя в базе. Второй запрос на запись ждёт завершения первого, затем читает актуальную занятость. SELECT FOR UPDATE здесь не используется.

Первый запрос:

1. Освобождает истёкшие брони этого сеанса.
2. Проверяет, что сеанс не начался, кресла принадлежат залу и не отключены.
3. Проверяет отсутствие активных `BookingSeat`.
4. Сохраняет заказ, цену и кресла; фиксирует транзакцию.

Второй запрос после ожидания увидит занятую запись и вернёт понятную ошибку. Дополнительная защита — уникальный индекс `(SessionId, SeatId, Active)`.

`Active = 1` означает, что заказ удерживает кресло. `Active = NULL` означает историческую запись. SQLite допускает несколько NULL в уникальном индексе, поэтому отменённые и просроченные заказы сохраняются, а кресло может снова продаваться. Ограничение CHECK не допускает другие значения Active. CHECK проверяется SQLite.

## Состояния заказа

```text
Ожидает оплаты ── оплата до срока ──> Оплачен ── возврат до сеанса ──> Возвращён
       │
       ├── отмена пользователем/менеджером ──> Отменён
       └── прошло 10 минут ─────────────────> Срок истёк
```

Активное удержание остаётся у ожидающих и оплаченных заказов. После отмены, истечения срока или возврата Active становится NULL. При возврате запись Payment сохраняется с IsRefunded=true, а билет больше не открывается. Для оплаченного заказа обычная отмена запрещена: менеджер должен использовать возврат.

Фоновая задача каждые 30 секунд очищает просроченные брони. Это не единственная проверка: схема кресел, создание заказа и оплата также проверяют срок. Даже если фоновая задача временно не работает, просроченную бронь оплатить нельзя.

Все изменения брони, включая оплату, возврат и очистку, сначала начинают транзакцию записи SQLite. Оплата и очистка не смогут одновременно считать одну бронь и оплаченной, и истёкшей. Уникальная связь Payment.BookingId делает повторную оплату идемпотентной.

## Расписание и изменение залов

Администратор при создании сеанса начинает транзакцию записи SQLite до проверки расписания. Пересечение определяется условием:

```text
существующее_начало < новое_окончание
И существующее_окончание > новое_начало
```

Окончание рассчитывает сервер: начало + длительность + 20 минут уборки. Проверка под блокировкой не позволяет двум администраторам одновременно вставить пересекающиеся сеансы. Изменение кресел также выполняется в транзакции записи: параллельный покупатель не сможет купить отключаемое место.

Купленные билеты ссылаются на фильм/сеанс/кресло, поэтому поля, меняющие смысл уже созданного заказа, запрещено редактировать. Цена конкретного кресла дополнительно сохраняется в BookingSeat, а итог — в Booking.

## Защита

- Роли проверяются атрибутами `[Authorize(Roles = ...)]` на контроллерах и действиях.
- Пользовательские заказы ищутся одновременно по `Id` и `UserId`. Поле владельца не принимается из формы.
- Все POST-формы используют AntiForgery. Прямой POST без токена получает 400.
- Изменение ролей/блокировка обновляет security stamp. Проверка выполняется при каждом запросе.
- Данные форм ограничены Bind/ViewModel и DataAnnotations; пользователь не может подставить цену, статус оплаты, роль при регистрации или одобрение отзыва.
- Запросы LINQ параметризуются EF Core. Провайдер — Microsoft.EntityFrameworkCore.Sqlite; ручные MySQL-запросы отсутствуют.
- Razor экранирует текст; Html.Raw для пользовательского содержимого не используется.
- Загрузка постеров ограничена размером и сигнатурой JPEG/PNG; SVG не принимается из формы, имя генерируется сервером.
- Публичные чтения используют AsNoTracking, запросы асинхронные; большие административные списки, заказы и отзывы имеют страницы.

## SQLite и первый запуск

Program.cs подключает SQLite, создаёт App_Data и применяет InitialSqlite. SeedData добавляет начальные данные без дубликатов. База — один локальный файл; сервер MySQL не требуется. CinemaDesignTimeFactory позволяет EF CLI создавать миграции, не запуская веб-приложение. Денежные значения decimal не преобразуются в double; статистика суммируется в C#.
